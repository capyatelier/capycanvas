# Capy Canvas for macOS and iPadOS

[macOS and iPadOS development](../../docs/development/apple.md)

One app family with two native hosts: AppKit on macOS and UIKit on iPadOS. Both
present the shared Rust editor through one SwiftUI editor and one Rust bridge,
`layer-apple`, which wraps the `layer-host` session facade that Android also
uses. The document, engine, UI policy, catalog and rendering stay in shared Rust.
The full-window Metal canvas sits behind the editor controls and header.

Setup, build, run and test commands are in the
[development guide](../../docs/development/apple.md); porting rules are in the
[Apple porting guide](../../docs/APPLE_PORTING_GUIDE.md).

## Layout

| Path | Contents |
| --- | --- |
| `Shared/Bridge/` | Swift side of the bridge: the serial owner, snapshot state, frame driver, persistence, recovery, input records, trace recorder and drawing workloads |
| `Shared/Editor/` | SwiftUI editor views used by both targets |
| `Shared/Settings/` | Settings and shortcut pages |
| `Shared/Tests/` | XCTest journeys compiled into both UI test targets |
| `iOS/`, `macOS/` | Per-platform `App` entry points, `Canvas` Metal views, `Input` adapters, `Platform` services and platform-only `Tests` |
| `native/` | The `layer-apple` Rust crate: the C ABI in `include/CapyApple.h`, Metal surface ownership, document workers and the Rust tests (`src/*_tests.rs`) |
| `tests/` | Standalone Swift and Python fixtures that run without XCTest |
| `scripts/` | Build, project and resource generation, fixture runners and the command audit |
| `CapyCanvas.xcodeproj` | Tracked, generated by `scripts/project.py` |
| `Generated/` | Ignored resources written by `scripts/prepare.py` |
| `command-coverage.json` | Apple review of every shared command, checked by `scripts/audit-commands.py` |

## Where to start reading

- `native/include/CapyApple.h` documents ownership, packed sample units, return
  values and borrowed versus owned strings for every C call.
- `native/src/lib.rs` implements the ABI over `layer_host::NativeHost`.
- `Shared/Bridge/NativeOwner.swift` and `EditorStore.swift` run every Rust call
  on one serial owner per editor window and publish its results.
- `Shared/Bridge/EditorSnapshotState.swift` and `WorkspaceMotion.swift` turn
  published snapshots into observable SwiftUI state.
- `Shared/Bridge/CanvasFrameDriver.swift` admits canvas frames.
- `Shared/Editor/EditorView.swift` is the editor root.
- `iOS/Canvas/MetalCanvas.swift` with `iOS/Input/PencilInput.swift`, and
  `macOS/Canvas/MacMetalCanvas.swift` with `macOS/Input/MacInput.swift`, host
  the canvas and its input.
- `macOS/App/MacEditorCommands.swift` projects the shared menus into the OS menu
  bar.

## How it fits together

- **One owner per window.** Each editor window owns one `NativeHost` and one
  serial render executor. Input, snapshots, rendering and destruction all run
  there. The UI thread captures input samples and the displayed camera revision
  and submits owned buffers; packed input and GPU work never go through JSON.
  Errors and Rust unwinds are contained at each ABI call.
- **Snapshot publication.** Request 7 returns `NativeHost::take_layout_update_bytes`
  serialized straight to UTF-8, with `display_status` and `document_tabs`
  appended by `layer_host::extend_update`. A full snapshot sets
  `workspace_update.model_revision`; later motion packets must match it and
  only move geometry, tab previews and drop hints. `EditorSnapshotState` keeps
  one immutable snapshot and exposes live field, command, panel and menu
  readers, so SwiftUI reevaluates only views whose values changed. Document and
  lifecycle code takes an explicit whole-snapshot copy with `.json`.
- **Frames.** The frame driver allows one queued render operation and lets the
  `CAMetalLayer` manage drawable availability. Presentation callbacks only feed
  diagnostics, so rendering never waits for them. Resume requests a fresh frame,
  and surface generations stop old replies from reaching a replacement view.
  Shaders are prepared on demand as described in
  [shared shader readiness](../../docs/internals/shared-shader-readiness.md).
- **Menus and chrome.** macOS top-level menus use the OS menu bar and target the
  focused editor window; the iPad keeps in-app menus. Both use the same shared
  catalog and one menu implementation. Popups use opaque shared-theme surfaces
  (`EditorPopupSurface`, `EditorPopupPresentation`); Settings keeps an opaque
  native background.
- **Files and storage** run on workers off the render owner; see
  [Apple persistence](PERSISTENCE.md). Pencil, tablet and trackpad handling is in
  [Apple input](INPUT.md), and trace recording and workloads are in
  [Apple performance](PERFORMANCE.md).
